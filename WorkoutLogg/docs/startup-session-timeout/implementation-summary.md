# Результат

Ветка `main`. Ошибка возникает в восстановлении сохранённой сессии до отображения AppShell.

## Изменения

- Инициализация запускается из одноразового Loaded стартовой страницы; fire-and-forget вызов из CreateWindow удалён.
- Тайм-аут, ошибка подключения, неуспешный / пустой ответ CurrentUser и прочие ошибки инициализации заменяют загрузку экраном ошибки с кнопками повтора и входа.
- Сетевое исключение не удаляет токены. Ответы 401 / 403 переводят на вход; существующее поведение AuthHeaderHandler / refresh не менялось.
- Повторная попытка создаёт новую загрузку и повторяет восстановление сессии; одновременное повторное нажатие блокируется отключением кнопки.
- Успешный CurrentUser сохраняется в CurrentUserStore перед выбором страницы.
- Переход к Dashboard подписывается на Loaded до установки Shell в окно, обработчик одноразовый и перехватывает ошибки навигации.
- В Debug добавлены сообщения `[Startup]`. Новые пользовательские сообщения локализованы.

## Проверки

- Android ARM64 Debug: сборка успешна, 0 ошибок, 214 предупреждений, около 17 секунд.
  Проверен `WorkoutLogg/WorkoutLogg.csproj`, `net10.0-android`, `android-arm64`,
  `--no-restore`, установленный JDK 21.
- `git diff --check`: успешно.
- API на компьютере ответил `Healthy`, HTTP 200 на HTTPS `/alive` (curl с `-k`).
- Список ADB reverse подтвердил восстановленные пробросы 5001 / 5000.

## Ручная проверка и ограничения

Согласно предыдущему выбору пользователя, обновлённое приложение не устанавливалось
агентом на телефон. После повторного запуска из IDE проверить:

1. Сохранённая сессия и доступный API: открывается нужный шаг онбординга или Dashboard.
2. Недоступный API / отсутствующий reverse: после ошибки запроса открывается экран
   ошибки, а не постоянная LoadingPage.
3. Восстановить связь и нажать повтор: сессия восстанавливается без ручного ввода пароля,
   если токен ещё действителен.
4. Кнопка входа открывает LoginPage; отсутствие сохранённого токена сразу открывает LoginPage.
5. Повторное появление Shell не запускает повторно одноразовый обработчик Loaded.

Воспроизведение тайм-аута и повторной попытки в мобильном UI ещё не проверено.
ADB reverse восстановлен, API оставлен работающим.

Модульной памяти в целевом репозитории нет, она не обновлялась. Результаты задачи
сохранены здесь, инструкция повторной попытки добавлена в README.

## Повторный тайм-аут при работающем API

- Пользователь предоставил стек `System.TimeoutException` с `AndroidMessageHandler.ConnectAsync`.
- Проверка подтвердила: API на 5001 отвечает `Healthy`, ADB reverse 5001 / 5000 присутствует,
  системный HTTP proxy на телефоне не задан.
- В текущем `MauiProgram.cs` условие определения эмулятора снова проверяло только Android-платформу.
  При текущем bundled-конфиге это выбирало `https://10.0.2.2:5001` и для физического Samsung.
- Восстановлена проверка `DeviceInfo.DeviceType == DeviceType.Virtual`. Для физического телефона
  локальный адрес — `https://localhost:5001` через ADB reverse.
- В Debug / Android logcat добавлена строка `[ApiEndpoint]` с платформой, типом устройства,
  флагом локального режима и адресом без заголовков / токенов.
- В старте, регистрации и входе `TimeoutException` распознаётся вместе с `OperationCanceledException`.
- Повторная Android ARM64 сборка: 0 ошибок, 213 предупреждений; `git diff --check` пройден.
- Обновлённое приложение на телефон агентом не устанавливалось. Нужно полностью перезапустить
  клиент из IDE, чтобы заново выполнился `CreateMauiApp`; Hot Reload не пересоздаёт HTTP-клиенты.
  Ожидаемая диагностика на Samsung: `DeviceType=Physical`, `Address=https://localhost:5001`.
