# React-приложение и схемы фитнес-залов

## Запуск

Команды ниже выполняются из папки `WorkoutLogg`. Нужны .NET SDK 10, Node.js
22.12+ и pnpm. Секреты остаются в существующем `.env`; не перезаписывайте его.

```powershell
docker compose up -d postgres redis
dotnet run --project WorkoutLogger.WebApi --launch-profile https
```

В другом терминале:

```powershell
cd WorkoutLogger.Web
pnpm install --frozen-lockfile
pnpm dev
```

Открыть `http://localhost:5173`. По умолчанию это прежняя организация
WorkoutLogg с существующими данными. Если API работает на другом порту:

```powershell
$env:API_PROXY_TARGET = 'https://localhost:5061'
pnpm dev
```

Vite сохраняет исходный Host при проксировании запросов. Исключение проверки
сертификата действует только в локальном Vite proxy. Production использует
один origin для React и API, HTTPS и обычную проверку сертификатов.

## Подключение залов

При первом использовании скопировать `WorkoutLogger.WebApi/appsettings.Tenants.example.json`
в `WorkoutLogger.WebApi/appsettings.Tenants.json` (последний исключён из Git).
Если файл уже существует, редактировать его без перезаписи настроек.

Каталог имеет вид:

```json
{
  "Tenancy": {
    "Tenants": [
      {
        "Id": "legacy",
        "Name": "WorkoutLogg",
        "Hosts": ["localhost", "127.0.0.1", "10.0.2.2"],
        "OwnerUserIds": []
      },
      {
        "Id": "atlas",
        "Schema": "gym_atlas",
        "Name": "Atlas Fitness",
        "Hosts": ["atlas.localhost"],
        "OwnerUserIds": []
      }
    ]
  }
}
```

После перезапуска API миграции создадут схемы новых залов. Для разработки
поддомены `*.localhost` в браузере направляются на loopback. Для реального
домена настроить DNS, TLS и reverse proxy, сохраняющий Host. В `Hosts` нет
протокола, порта, пути или wildcard. Неизвестный домен получает 404. Для доступа
по LAN/VPS-IP явно добавить этот адрес в Hosts нужного зала.

Для назначения первого администратора:

1. Зарегистрировать аккаунт на домене нужного зала.
2. В профиле открыть «Идентификатор аккаунта».
3. Оператор добавляет этот ID в `OwnerUserIds` именно этого зала и перезапускает API.
4. После повторного входа появится «Управление клубом».

Регистрация сама по себе не выдаёт административные права. Один email может
иметь разные аккаунты и пароли в разных залах. При переименовании домена
сохранять `Id` и `Schema`: они являются идентичностью организации.

## Данные и миграции

Схема должна соответствовать `gym_[a-z0-9_]{1,46}`, быть уникальной и задаваться
только оператором. Приложение не принимает имя схемы из query/header/body.
Каждый новый зал получает все таблицы пользователей, тренировок, тренеров,
кошельков, чатов, подписок и контента в одной своей схеме, а также таблицы
`__UsersMigrations`, `__TrainersMigrations`, `__SubscriptionsMigrations`,
`__SiteMigrations`. У `legacy` сохранена прежняя общая история EF.

`TenantModelCacheKeyFactory` различает контекст, схему и designTime. Runtime
контексты обращаются к таблицам с явно заданной схемой. Миграционные контексты
строят каноническую модель, чтобы проверка snapshot не давала ложных изменений.
`TenantMigrationsSqlGenerator` перенаправляет операции и внешние ключи,
сохраняя исходные операции после генерации. Произвольный `migrationBuilder.Sql`
и удаление схем отклоняются: такие миграции требуют отдельной реализации и
проверки. Исключение — точный SQL создания истории, сформированный Npgsql.
При обновлении EF/Npgsql обязательно повторять интеграционный тест миграций.

Миграции выполняются до приёма запросов. Для отдельного шага развёртывания:

```powershell
dotnet run --project WorkoutLogger.WebApi --launch-profile https -- --Tenancy:MigrationOnly true
```

После этого на рабочих экземплярах можно задать `Tenancy__MigrateOnStartup=false`.
При нескольких экземплярах provisioning новых схем выполнять одним deployment job.
Миграции не копируют автоматически старые данные из `legacy` в новый зал.
Схемы изолируют запросы приложения, но не являются границей PostgreSQL-прав:
используется один технический пользователь БД. Доступ владельца зала к SQL не выдаётся.

## Сессии и фоновые процессы

JWT содержит `tenant_id`; запросы и refresh отклоняют токен другого зала.
Старые токены без tenant claim допускаются только для `legacy`. Браузер хранит
защищённую Data Protection пару токенов в host-only HttpOnly SameSite=Strict
cookie, access token — только в памяти. Изменение браузерной сессии требует
совпадения Origin и Host. Production cookie всегда Secure.

За reverse proxy необходимо настроить ASP.NET forwarded headers **для доверенного
proxy**, чтобы `Request.Scheme` оставался HTTPS. Не разрешать произвольные
X-Forwarded-Host от клиента. Data Protection key ring должен сохраняться между
рестартами и быть общим для экземпляров одного deployment; ключи и секреты
не помещать в репозиторий. JWT signing key берётся из существующей конфигурации.

Кеш и лимиты входа включают ID зала. Outbox обходит каждый зал в отдельном scope,
ошибка одного зала не прекращает обработку остальных. Live-события разделены
по `(tenantId, workoutId)`, подписка доступна владельцу тренировки и принятому
тренеру этого ученика.

## Админка

Настройки сохраняются в `site_settings` схемы зала. Сохранение создаёт черновик,
публикация копирует его в опубликованную версию. Номер версии защищает от
перезаписи параллельных изменений. Публичный `/api/site` возвращает только
опубликованные данные; `/api/admin/*` требует серверного права `GymAdmin`.

Карточку тренера администратор связывает с существующим аккаунтом клуба.
Для новых залов участник не может самостоятельно создать публичную карточку
через старый MAUI API или снова включить скрытую администратором карточку.

Платёжные настройки новых залов задаются отдельно в
`Tenancy:Subscriptions:<tenantId>`, с полями `SubscriptionSettings`.
Общие секреты `SubscriptionSettings` используются только `legacy`. Браузерный
интерфейс пока показывает и восстанавливает подписку; checkout, веб-возврат и
webhook-сценарии каждого зала требуют отдельной настройки и проверки.

## Сборка и проверка

```powershell
cd WorkoutLogger.Web
pnpm build
cd ..
./tools/Publish-Web.ps1
dotnet publish WorkoutLogger.WebApi -c Release
dotnet test Modules.Users.Tests -c Release
```

`Publish-Web.ps1` копирует сборку в `WebApi/wwwroot`. API обслуживает статические
файлы и SPA routes на том же домене. Сам файл приложения не содержит секретов
или фиксированного адреса другого зала.

Для интеграционных тестов PostgreSQL задать `TENANCY_TEST_DB` локальной строкой
подключения и выполнить:

```powershell
dotnet test Modules.Users.Tests -c Release --filter FullyQualifiedName~TenancyTests
```

Тест создаёт только случайные схемы `gym_test_*`, выполняет миграции дважды,
проверяет одинаковые email/ID в разных схемах и удаляет свои схемы в `finally`.
Без `TENANCY_TEST_DB` этот тест пропускается; остальные проверки запускаются.

Для изучения React: начать с `src/App.tsx` (сессия, темы, маршруты), затем
`src/pages/Workouts.tsx` (управляемая форма), `src/pages/Admin.tsx`
(редактор/публикация), `src/hooks.ts` и `src/api.ts` (запросы и обновление токена).

Клубные абонементы, карты/браслеты и учёт присутствия: [инструкция](club-memberships.md).
